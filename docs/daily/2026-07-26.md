## backend-developer — S4.5 (Vague 4, `/refacto` audit-v1)

Séparation de domaine de la clé Fernet tv-auth (AUDIT-P2-003 / CR-S04) : `payload_crypto.get_fernet()` dérivait `sha256(AI_API_KEY)` **sans** tag de séparation de domaine quand `TV_AUTH_ENCRYPTION_KEY` est vide, contrairement à `crypto_fields.get_xtream_fernet()` (même repli, mais avec `_KEY_DERIVATION_CONTEXT` dédié) — le secret bearer d'auth API servait donc, verbatim, de clé de chiffrement au repos pour des payloads portant des tokens Plex. Ajout d'un `_KEY_DERIVATION_CONTEXT = b"plexhub.tv_auth_payload.v1:"` symétrique, préfixé avant `AI_API_KEY` dans le SHA-256 — convention strictement calquée sur `crypto_fields.py` (même mécanisme, tag différent). `TV_AUTH_ENCRYPTION_KEY` explicite reste prioritaire et **inchangée** ; les déploiements qui l'ont déjà configurée ne subissent rien. **Rupture assumée** (acceptée par l'utilisateur) : les sessions d'appairage TV en cours au moment du déploiement, sur un déploiement en dérivation implicite, deviennent indéchiffrables — le code existant (`tv_auth.py::get_status`, déjà en place, non modifié) attrapait déjà `PayloadDecryptError` proprement en **503** (`"Pairing payload unavailable"`), jamais un 500 ; fenêtre de casse = `TV_AUTH_TTL_SECONDS` (900 s par défaut), la TV relance simplement l'appairage. Note d'exploitation ajoutée dans `.env.example` (bloc `TV_AUTH_ENCRYPTION_KEY`). Fail-closed préservé : `get_fernet()` reste `None` si `TV_AUTH_ENCRYPTION_KEY` et `AI_API_KEY` sont tous deux vides (503 "not configured" inchangé). Nouveau `tests/test_payload_crypto.py` (7 tests) : non-collision prouvée avec la clé Xtream dérivée du même `AI_API_KEY` (un token chiffré par l'une échoue `InvalidToken` sous l'autre), formule de dérivation épinglée, priorité de la clé explicite, roundtrip normal, token de l'ancienne dérivation → `PayloadDecryptError` propre (pas de crash), fail-closed préservé, aucune clé dans les logs d'erreur. Suite ciblée : `test_payload_crypto.py` (7 passed) + `test_tv_auth.py` (27 passed, aucune régression). `ruff check` vert sur les fichiers touchés. Périmètre strict respecté (`app/utils/payload_crypto.py`, `.env.example`, `tests/test_payload_crypto.py` ; `app/config.py`/`crypto_fields.py` non touchés — aucune nouvelle clé de config nécessaire, `TV_AUTH_ENCRYPTION_KEY` existait déjà). Commit scope vérifié via `git show --stat HEAD`.

## backend-developer — S4.2 (Vague 4, `/refacto` audit-v1)

Rate-limit CIBLÉ + cap de sessions `pending` (AUDIT-P2-004 / CR-S05) — décision utilisateur déjà tranchée, appliquée telle quelle : **pas de limiteur global** (PlexHubTV poll plusieurs endpoints authentifiés légitimement, dont `GET /tv-auth/status` en boucle serrée pendant l'appairage — un throttle global la casserait), et le brute-force générique X-API-Key/Basic-Auth reste délégué au WAF/ingress (même doctrine déjà actée pour `/dav`, §9 piège 18b) — **documenté explicitement**, jamais laissé croire que le backend s'en charge. **Seul `POST /api/tv-auth/start` est limité** : c'est le seul endpoint non-authentifié qui écrit une ligne en base à chaque appel. Nouveau module `app/utils/rate_limit.py` (aucune logique dans `main.py` — pas touché du tout, le verrou V-1 ≤10 lignes est donc trivialement respecté à 0 ligne) : `SlidingWindowLimiter` (compteur glissant per-clé, process-local, in-memory, `dict[str, deque[float]]`, borné à 5000 clés trackées pour survivre à un spoofing d'IP) exposé en **deux instances séparées** — fenêtre courte (`TV_AUTH_START_RATE_LIMIT_MAX=5`/`TV_AUTH_START_RATE_LIMIT_WINDOW_SECONDS=60`, défauts) qui ralentit un flood naïf, et fenêtre longue calée sur le TTL de session (`TV_AUTH_PENDING_SESSIONS_CAP_PER_IP=20` sur `TV_AUTH_TTL_SECONDS`) qui approxime (sur-compte volontairement, jamais sous-compte) le nombre de sessions non-expirées créées par une IP apparente — plus `check_pending_cap()`, LA vraie protection : un `COUNT(*) WHERE status='pending'` **DB-authoritative, global (pas par IP)** contre `TV_AUTH_PENDING_SESSIONS_CAP=500`, câblé dans le `_work` de `tv_auth.start()` (mêmes garanties replay-safe que le reste du patron `write_with_retry`/ADR 0004 — une exception métier `PendingCapExceeded` traverse `run_with_retry` sans jamais être retentée, exactement comme `_UserCodeExhaustedError` déjà en place). Client identifié par `resolve_client_ip()` (miroir volontairement dupliqué — pas importé — de `deps._client_ip` : `CF-Connecting-IP` puis `X-Forwarded-For` puis `request.client.host`) avec **honnêteté documentée** : ces en-têtes sont usurpables si ce process est joignable hors du tunnel Cloudflare, ce qui rendrait les deux limiteurs par-IP inopérants — raison structurelle pour laquelle le cap global (2) ne dépend PAS de l'identification IP et tient même sous usurpation totale. Rejet = **429 + `Retry-After`** (jamais 500/403), même sémantique que le 503+`Retry-After` déjà en place pour le throttle DAV. `app/config.py` (append-only, 3 clés + log de boot documentant la doctrine), `.env.example` (append). Tests : `tests/test_rate_limit.py` (19 tests — unitaires sur `SlidingWindowLimiter`/`check_pending_cap`/`resolve_client_ip` avec horloge fake via `now=`, + intégration HTTP réelle prouvant N+1→429+Retry-After, cap global atteint même depuis une IP neuve, IP différente non pénalisée, `/api/health` et `/dav` jamais limités, **`/tv-auth/status` jamais limité même après épuisement du budget `/start` du même client** — la garantie non-régression explicitement exigée). Bug trouvé et corrigé en écrivant les tests : off-by-one de fenêtre glissante (`events[0] < window_start` au lieu de `<=` — un événement vieux d'exactement `window_seconds` restait compté un tick de trop). Fixture autouse `_reset_rate_limiters` ajoutée dans `tests/conftest.py` (les deux singletons `SlidingWindowLimiter` sont un état process-local qui survit à toute la session pytest — sans reset, un test antérieur épuiserait le budget d'un test non lié partageant la même IP apparente par défaut du transport ASGI). Suite ciblée : `test_rate_limit.py` + `test_tv_auth.py` + `test_auth_guard.py` + `test_router_http_coverage.py` = **105 passed**, aucune régression sur le device-flow. `ruff check` vert. Boot `uvicorn app.main:app` (shim `fcntl` Windows, DATA_DIR/LOG_DIR isolés) → `GET /api/health` 200. Périmètre strict respecté (`app/utils/rate_limit.py`, `app/api/tv_auth.py`, `app/config.py`, `.env.example`, `tests/test_rate_limit.py`, `tests/conftest.py` ; `app/main.py`/`app/api/deps.py`/`app/api/csrf.py` non touchés).
