## Résumé

Une TV neuve n'a pas de clé : elle demande une session au backend, affiche un code court (et un QR), puis interroge le backend jusqu'à ce qu'un appareil déjà configuré valide ce code et lui confie une configuration (jeton Plex, URL du backend, clé API). Le backend chiffre cette configuration au repos, ne la livre qu'une fois à la TV, puis la détruit à l'acquittement. Trois des quatre endpoints du flux sont publics ; le quatrième, `POST approve`, exige une clé API. Depuis le Lot 10 (sous-lot B), l'adresse affichée par la TV (`verificationUri`, aussi le contenu du QR) ouvre une **page HTML publique** servie par le backend (`GET /api/tv-auth/approve`) : le téléphone y saisit le code et la clé, et la page appelle elle-même `POST approve` (voir FR-BE-075). `approve` reste le seul point d'entrée que la TV n'appelle pas. Personas : spectateur TV, appareil d'appairage.

## Règles métier

- **RG-BE-03.1** — Machine d'états d'une session : `pending` → `approved` → `completed` ; `pending` ou `approved` → `expired` dès que l'heure dépasse `expires_at` (borne incluse : à `expires_at` exactement, la session vit encore). — preuve `app/api/tv_auth.py:91-94`, `app/api/tv_auth.py:220-223`
- **RG-BE-03.2** — Le payload est livré à la TV au **sondage**, pas à l'acquittement : la livraison est marquée avant l'envoi de la réponse. Si la réponse est perdue, les sondages suivants renvoient `approved` sans payload et la TV doit relancer un appairage. — preuve `app/api/tv_auth.py:624-639`, `tv:app/src/main/java/com/chakir/plexhubtv/feature/pairing/PairingViewModel.kt:138-143`
- **RG-BE-03.3** — Le plafond global est le seul garde qui tienne sous usurpation d'IP (`CF-Connecting-IP` et `X-Forwarded-For` sont posés par l'appelant hors tunnel) ; les limiteurs par IP sont une courtoisie. Le comptage porte sur le statut littéral `pending` : des sessions expirées jamais relues comptent jusqu'à leur purge à `expires_at` + 1 h. — preuve `app/api/tv_auth.py:330-344`, `app/utils/rate_limit.py:210-223`, `CLAUDE.md` §9 piège 19(d)
- **RG-BE-03.4** — Le limiteur court enregistre son passage avant l'évaluation du second : un refus du second laisse le passage du premier compté. Un appel refusé n'est pas enregistré dans le limiteur qui le refuse. — preuve `app/api/tv_auth.py:264-284`, `app/utils/rate_limit.py:140`
- **RG-BE-03.5** — Un payload posé par `approve` sur une session déjà livrée est impossible (409 dès que le statut n'est plus `pending`) ; en revanche `approve`, `complete` et l'expiration écrivent par `UPDATE` aveugle sur l'identifiant, sans condition de statut : deux appels concurrents peuvent réussir tous deux (dernier écrivain gagnant). — preuve `app/api/tv_auth.py:227-235`, `app/api/tv_auth.py:525-537`, `app/api/tv_auth.py:682-694`
- **RG-BE-03.6** — Côté TV, le sondage attend un intervalle avant le premier appel, double le délai à chaque échec (plafond 60 s, remise à la base au premier succès), n'interroge plus au-delà du TTL local et traite 404 et 410 du sondage comme « expiré ». — preuve `tv:app/src/main/java/com/chakir/plexhubtv/feature/pairing/PairingViewModel.kt:80-132`, `tv:data/src/main/java/com/chakir/plexhubtv/data/repository/TvPairingRepositoryImpl.kt:72-75` · test `tv:app/src/test/java/com/chakir/plexhubtv/feature/pairing/PairingViewModelTest.kt:224-271`
- **RG-BE-03.7** — Côté TV, une configuration reçue est applicable si elle porte un jeton Plex, ou une URL de backend **et** une clé API ; l'URL et la clé sont enregistrées avant que le jeton Plex ne soit testé, donc un jeton refusé laisse la configuration backend déjà écrite. — preuve `tv:domain/src/main/java/com/chakir/plexhubtv/domain/model/TvPairing.kt:46-47`, `tv:domain/src/main/java/com/chakir/plexhubtv/domain/usecase/pairing/ApplyTvPairingPayloadUseCase.kt:36-63`
- **RG-BE-03.8** — La page `GET /api/tv-auth/approve` est publique par construction : elle rend un gabarit statique, ne dépend ni de `get_db` ni de la clé Fernet et ne porte aucune donnée de session. Elle reste donc servie même quand le chiffrement n'est pas configuré (alors que `POST approve` répond 503), et ne permet aucun lookup côté serveur pour valider le code avant l'envoi. — preuve `app/api/tv_auth.py:436-469` · test `tests/test_tv_auth_approve_page.py:343-349`
- **RG-BE-03.9** — La page porte des en-têtes de sécurité propres (aucun middleware global n'existe) : `Content-Security-Policy` à nonce (un nonce neuf par requête, `default-src 'none'`, scripts et styles limités aux deux blocs inline portant le nonce, `connect-src 'self'`, `form-action 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`), `X-Frame-Options: DENY`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`. Le gabarit n'embarque aucune ressource externe ni gestionnaire inline, et l'échappement Jinja2 reste actif. — preuve `app/api/tv_auth.py:417-433`, `app/templates/pairing/approve.html:1-16` · test `tests/test_tv_auth_approve_page.py:113-158`
- **RG-BE-03.10** — La page est limitée par IP (limiteur dédié, indépendant de ceux de `start`) : 30 requêtes par fenêtre glissante de 60 s par défaut (`TV_AUTH_APPROVE_PAGE_RATE_LIMIT_MAX` et `_WINDOW_SECONDS`, une valeur ≤ 0 désactive), 429 avec `Retry-After` au-delà. — preuve `app/api/tv_auth.py:436-469`, `app/utils/rate_limit.py:247-249`, `app/config.py:97-105` · test `tests/test_tv_auth_approve_page.py:215-253`
- **RG-BE-03.11** — La clé d'autorisation saisie dans la page n'est envoyée qu'en en-tête `X-API-Key` par un `fetch` vers l'URL relative `approve` (même origine, derrière tunnel ou reverse-proxy), champ `password` sans autocomplétion, `credentials: omit`, jamais placée dans une URL, un cookie ni un stockage web ; les champs secrets sont vidés après un succès. — preuve `app/templates/pairing/approve.html:70`, `app/templates/pairing/approve.html:240-246` · test `tests/test_tv_auth_approve_page.py:161-168`, `tests/test_tv_auth_approve_page.py:260-285`

## Questions ouvertes

- Quel client réalise `approve` en pratique ? Depuis le Lot 10, la page `GET /api/tv-auth/approve` ; un autre client (script, appli mobile) reste possible. Le QR mène désormais à une page exploitable (`tests/test_tv_auth_approve_page.py:288-311`). — à confirmer sur une instance réelle, derrière le tunnel.
- Le `deviceCode` circule en query string sur `GET /status` : figure-t-il en clair dans le journal d'accès d'uvicorn (aucun filtre ni `--no-access-log` relevé dans le code) ? — à vérifier par test : lancer l'image, sonder, lire la sortie du conteneur.
- `verificationUri` dépend de `request.base_url` : derrière le tunnel ou un reverse-proxy, le schéma et l'hôte renvoyés sont-ils ceux que la TV et le téléphone peuvent joindre ? — à vérifier par test : `start` appelé via l'ingress réel.
- Une `OperationalError` persistante sous verrou SQLite sur `start`, `approve` ou `complete` remonte-t-elle bien en 500 brut, sans corps exploitable par la TV ? — à vérifier par test (modèle : `tests/test_tv_auth.py:773-848`, avec un verrou tenu au-delà des retries).
- Une TV dont la réponse de sondage est perdue après le marquage de livraison n'a aucun moyen de récupérer le payload : est-ce le comportement voulu ou faut-il une re-livraison bornée ? — décision produit, code muet.
- Le mobile qui approuve envoie-t-il d'autres clés que `plexToken`, `backendUrl` et `apiKey` (comptes Xtream par exemple) ? Le backend les stocke et les livre, la TV les ignore. — à vérifier par test, une fois le client d'approbation identifié.
