# Pièges connus — DB, SQLite WAL, migrations et sauvegardes

- **[#6]** **Migrations idempotentes** : tout DDL en `IF NOT EXISTS` / `ADD COLUMN` gardé ; nouvelle migration **en fin** de `run_migrations()`. **Ordre d'exécution : 001-007, puis 008 (sur connexion dédiée), puis 009→032**. M008 (`ai_embeddings` vec0 `FLOAT[384]` + `ai_tmdb_cache`) **dépend du chargement de sqlite-vec** (`register_sqlite_vec_listener`, `database.py:25-54`). Migration courante = **032** (lot B4 : colonnes `media` du scrape, ADR 0013). Chaîne réelle : 010 `tmdb_scrape_cache`+`existing_summary`, 011 `ai_subtitle_cache`, 012 `ai_media_blurb`, 013 `media.is_adult`, 014 `media` métadonnées NFO, **015** index `media` manquants (CR-P02), **016** chiffrement Xtream (CR-S03), **017** snapshot `media_group`/`media_group_member` (CR-P01), **018** `download_job`/`download_batch`, **019** tables Plex, **020** `media.file_size`, **021** `plex_media_item.genres`, **022** `omdb_scrape_cache` (cache OMDb keyé `imdb_id`, DDL byte-identique au modèle ORM `OmdbScrapeCache` — CR-C05), **023** `ANALYZE`, **024** `media.youtube_trailer`, **025** colonnes d'outage sur `xtream_accounts`, **026** `media.match_locked`/`match_source` (§5.14), **027** table `scrape_review` (§5.14), **028** unique `uix_epg_dedup` sur `epg_entries` après dédoublonnage (Lot 10-D), **029** table `scrape_cache` (Lot B1, passerelle de scraping), **030** `api_keys.scopes` (Lot B1, ADR 0008), **031** table `metadata_edits` (Lot B2, ADR 0011).

- **[#7]** **`fcntl.flock` = POSIX** : l'élection master-worker (`main.py:226-227`) ne fonctionne que sous Linux/Docker (pas Windows natif). Seul le master lance le scheduler ; fermer le fd libère le flock.

- **[#8]** **SQLite « database is locked »** : passer par `commit_with_retry` / `run_with_retry` (`db_retry.py:21`, délais 0.1/0.5/1.0 s au-dessus du **`busy_timeout=60000` (60 s)** + `connect_args timeout=60`, `database.py:15,90`). WAL activé. ✅ **`AUDIT-P1-001` RÉSOLU (lot `/refacto` audit v1)** : la primitive correcte est **`write_with_retry`** (`utils/db_retry.py`) — elle ouvre une **session NEUVE à chaque tentative**, seule façon valide de retenter après qu'un lock a invalidé la transaction. **13 call-sites convertis** (workers de sync/enrichment/health/backfill, `category_service`, routers `accounts`/`ai`/`tv_auth`). Les autres sont **délibérément laissés** sur `commit_with_retry` (devenu honnête : il documente et loggue qu'il ne retente pas) pour deux raisons légitimes : (a) **lecture-modification-écriture sur session partagée** — une session neuve lirait un snapshot WAL périmé (ex. `bulk_update_categories` → `update_media_category_visibility`) ; (b) **appel réseau upstream mêlé à l'écriture** — rejouer sous retry retaperait le provider jusqu'à 4× (`create_account`, `refresh_categories`, `get_channel_epg`).
  > 🔴 **PIÈGE ACTIF — ne « corrige » JAMAIS un retry en ajoutant `rollback()` puis en retentant sur la MÊME session.** SQLAlchemy expulse les objets `pending` au rollback : la tentative suivante commite **zéro ligne, sans lever d'erreur** — perte d'écriture **silencieuse**, strictement pire que le bug d'origine. Utiliser `write_with_retry`, point.
  > ⚠️ Deux vrais bugs ont été trouvés lors de cette conversion, uniquement parce que les tests utilisent un **vrai verrou WAL sur fichier** (et non une exception synthétique) : un `except Exception` qui avalait l'`OperationalError` et neutralisait le retry (`enrichment_backfill_worker`), et un **deadlock auto-infligé** créé en séparant un DELETE de son INSERT sur un SQLite mono-writer (`tv_auth.start`). **Tout nouveau writer critique doit être testé sous vrai lock** (modèle : `tests/test_db_retry_real_lock.py`, `tests/test_worker_write_retry_real_lock.py`).

- **[#23]** **Sauvegarde / restauration SQLite (Lot 10-A) — trois règles à ne pas défaire.** (a) **Ne JAMAIS laisser un `-wal`/`-shm` à côté d'un `plexhub.db` restauré** : SQLite rejoue le WAL périmé sur le fichier remplacé et corrompt la lecture — `restore_db` les supprime AVANT le `os.replace` (et après avoir conservé la base courante). (b) **Un backup n'est publié sous `plexhub-*.db` qu'après `integrity_check` ; ne pas écrire directement sous le nom final** (disque plein = fichier partiel qui ressemble à un backup valide, puis élagué comme les autres) ; le `.tmp` doit rester dans le MÊME dossier (même volume ⇒ `os.replace` atomique). Ne pas ajouter de `.db.tmp` au motif d'élagage : un `.tmp` récent peut être un backup en cours (le balayage > 1 h est séparé). (c) **`restore_db` ne doit pas exiger une base courante saine** : la copie préalable utilise `verify=False` avec repli en copie brute — une base corrompue est justement la raison d'une restauration. Le verrou `server_start.lock` s'ouvre en mode `"a"` (jamais `"w"` : ça tronquerait le pid écrit par le master). `fcntl` n'existe pas sous Windows : le script reste importable, le test réel de `flock` est `skipif`.
