# AGENTS.md — PlexHub Backend

## §1. Résumé
Backend **FastAPI** (Python, async) du stack PlexHub : miroir de bibliothèques **Xtream-IPTV** (VOD + séries + chaînes Live + EPG), enrichissement **TMDB**, validation de flux, génération de **bibliothèque Plex/Jellyfin** (NFO + arborescence + .strm/images), **recommandations IA** (embeddings + recherche vectorielle), **génération LLM** (Ollama/gemma4 : présentations + chat) et **appairage TV** device-flow. Consommé par l'app Android `PlexHubTV`. Le backend ne stocke **aucun historique utilisateur côté IA** : `ai_tmdb_cache` + `ai_embeddings` sont clés sur `tmdb_id`. Cible de déploiement **Docker/Linux** : l'élection master-worker s'appuie sur `fcntl.flock` (POSIX, `app/main.py:226-227`).

Le garde sqlite-vec s'applique à **TOUS** les endpoints `/api/ai`, y compris LLM pur (cf. piège 12).
3. **Épisodes/personnes non supportés par l'IA vectorielle** : ranking au niveau `movie`/`tv` uniquement (`Literal["movie","tv"]`, `ai.py:87,104`). `find_by_imdb_id` ignore défensivement `tv_episode_results`/`tv_season_results`/`person_results` (`tmdb_service.py:281`) → comptés en `resolutionFailed` et droppés.

5. **Le rebuild ne tourne JAMAIS au boot** : uniquement via `POST /api/ai/embed/rebuild` (`embedding_worker.py:3,132`). Idempotent : scan `embedded_at IS NULL`, curseur `tmdb_id > :cursor` (`embedding_worker.py:76`), `PAGE_SIZE=50`, DELETE-puis-INSERT sur `vec0` (UPSERT interdit sur table virtuelle, `embedding_worker.py:108-114`). 6. **Migrations idempotentes** : tout DDL en `IF NOT EXISTS` / `ADD COLUMN` gardé ; nouvelle migration **en fin** de `run_migrations()`. **Ordre d'exécution : 001-007, puis 008 (sur connexion dédiée), puis 009→031**. 8. **SQLite « database is locked »** : passer par `commit_with_retry` / `run_with_retry` (`db_retry.py:21`, délais 0.1/0.5/1.0 s au-dessus du **`busy_timeout=60000` (60 s)** + `connect_args timeout=60`, `database.py:15,90`). WAL activé. ✅ **`AUDIT-P1-001` RÉSOLU (lot `/refacto` audit v1)** : la primitive correcte est **`write_with_retry`** (`utils/db_retry.py`) — elle ouvre une **session NEUVE à chaque tentative**, seule façon valide de retenter après qu'un lock a invalidé la transaction. **13 call-sites convertis** (workers de sync/enrichment/health/backfill, `category_service`, routers `accounts`/`ai`/`tv_auth`). Les autres sont **délibérément laissés** sur `commit_with_retry` (devenu honnête : il documente et loggue qu'il ne retente pas) pour deux raisons légitimes : (a) **lecture-modification-écriture sur session partagée** — une session neuve lirait un snapshot WAL périmé (ex. `bulk_update_categories` → `update_media_category_visibility`) ; (b) **appel réseau upstream mêlé à l'écriture** — rejouer sous retry retaperait le provider jusqu'à 4× (`create_account`, `refresh_categories`, `get_channel_epg`).
> 🔴 **PIÈGE ACTIF — ne « corrige » JAMAIS un retry en ajoutant `rollback()` puis en retentant sur la MÊME session.** SQLAlchemy expulse les objets `pending` au rollback : la tentative suivante commite **zéro ligne, sans lever d'erreur** — perte d'écriture **silencieuse**, strictement pire que le bug d'origine. Utiliser `write_with_retry`, point.
> ⚠️ Deux vrais bugs ont été trouvés lors de cette conversion, uniquement parce que les tests utilisent un **vrai verrou WAL sur fichier** (et non une exception synthétique) : un `except Exception` qui avalait l'`OperationalError` et neutralisait le retry (`enrichment_backfill_worker`), et un **deadlock auto-infligé** créé en séparant un DELETE de son INSERT sur un SQLite mono-writer (`tv_auth.start`). **Tout nouveau writer critique doit être testé sous vrai lock** (modèle : `tests/test_db_retry_real_lock.py`, `tests/test_worker_write_retry_real_lock.py`).

19. **Garde-fous ajoutés par le lot `/refacto` audit v1 — ne pas les défaire par mégarde** :
    (a) **Assertion de boot sur les routes** (`app/api/route_audit.py`) : l'app **refuse de démarrer** si une route `/api/*` est publiée sans l'un des gardes connus (4 généraux reconnus par **identité de fonction**, plus les 4 gardes de scope `verify_scrape_scope`/`verify_scrape_admin_scope`/`verify_media_read_scope`/`verify_media_write_scope`, chacun accepté **sous son seul préfixe** (`scrape*` sous `/api/scrape/v1/`, `media.*` sous `/api/metadata/v1/` — table `_SCOPE_GUARD_PREFIXES`), pièges 26b et 27). L'allow-list publique est **exactement** 5 couples **(méthode, chemin)** : `GET /api/health`, `POST /api/tv-auth/start`, `GET /api/tv-auth/status`, `POST /api/tv-auth/complete` et la page `GET /api/tv-auth/approve` (`POST /api/tv-auth/approve` est gardé, et **doit** le rester). Ajouter une route `/api/*` sans garde casse le boot — c'est **voulu**, ne « répare » pas ça en élargissant l'allow-list.
    (b) **`/metrics` est authentifié** (Basic Auth dédiée `METRICS_USERNAME`/`METRICS_PASSWORD`, séparée d'`ADMIN_*` exprès : un scraper compromis ne doit pas ouvrir l'UI admin). ⚠️ **Sans `METRICS_PASSWORD` configuré, `/metrics` renvoie 503, pas 401** (fail-closed, même convention qu'`ADMIN_PASSWORD` — vérifié sur l'image v1.8.0) : un opérateur qui déploie sans poser les identifiants n'a **plus aucune métrique**, pas juste un scraper qui se plaint. `METRICS_PUBLIC=true` rouvre l'accès (WARNING au boot) — **filet de transition, jamais un état permanent**.
    (c) **CSRF `Sec-Fetch-Site`** sur POST/PUT/PATCH/DELETE `/admin*` : `cross-site` → **403**. Les **GET ne sont jamais interceptés** (les swaps HTMX passent). Header **absent ⇒ accepté** (fail-open assumé : un client sans ce header ne relaie pas non plus de Basic Auth ambiante). Les miroirs JSON `/api/admin/*` ne sont **pas** concernés (gardés par `X-API-Key`, pas d'auth ambiante ⇒ pas de surface CSRF).
    (d) **Rate-limit ciblé** `/tv-auth/start` uniquement. **`/tv-auth/status` n'est JAMAIS limité** (la TV le poll en boucle — le limiter casserait l'appairage). ⚠️ Les limiteurs **par IP sont contournables** (`CF-Connecting-IP`/`X-Forwarded-For` sont contrôlés par l'attaquant hors tunnel) ; le garde qui tient sous usurpation est le **cap global de sessions `pending`** (`COUNT(*)` en base, indépendant de toute identification client). Le brute-force générique reste **délégué au WAF** — le backend ne s'en charge pas, ne pas le supposer.
    (e) **SSRF** : `app/utils/ssrf.py` vet images + health-check **via `event_hooks` httpx**, qui se déclenchent **à chaque hop de redirection** — d'où la préservation de `follow_redirects=True`. ⚠️ **Limite résiduelle réelle** : rebinding DNS (la garde résout, httpx re-résout ensuite) ; `SSRF_DNS_CACHE_SECONDS` **élargit** cette fenêtre — compromis de débit, **pas** un gain de sécurité. Non couverts : `tmdb_service`, `omdb_service`, `xtream_service`, `ollama_service`, `plex_api_service`.
    (f) **Image non-root (uid 1000)** : sur des volumes créés par l'ancienne image root, `chown -R 1000:1000 ./data ./logs ./media ./downloads` est **obligatoire** — sinon `server_start.lock` échoue et l'instance bascule **esclave en silence** (scheduler et pipeline morts, healthcheck pourtant vert). Runbook `docs/32-ops-docker-nonroot.md`.

20. **Panne fournisseur (§5.13) — ne JAMAIS « simplifier » le masquage en réutilisant `is_active` ou `is_broken`.** `is_active` est un interrupteur global lu par `plex_generator/source.py`, `sync_worker`, `/dav` et `download_service` ; `is_broken` est exclu de la génération dès `STREAM_FILTER_BROKEN=true` (défaut). Basculer l'un ou l'autre pendant une panne **purge la bibliothèque Jellyfin générée** — le sinistre que cette feature existe pour empêcher. L'état d'outage vit dans `xtream_accounts.outage_strikes`/`outage_since` et n'est consommé que par les lectures `media_service`. (a) **Toute nouvelle lecture app sur `Media` doit passer `_outage_clause`** — y compris l'hydratation du snapshot `media_group`, sinon le chemin de browse **par défaut** contourne entièrement la feature. (b) Le set masqué fait partie de la **clé de cache** de `get_unified_list` : ne pas l'en retirer. (c) `record_trip`/`record_clear` prennent un **`session_factory` explicite** et l'appelant fournit le sien (le pool worker) : laisser le service en choisir un a réellement envoyé le strike sur le pool API pendant que le worker tournait sur une autre base. (d) Le trip du pipeline est enregistré **après** `db.rollback()` + `db.expunge_all()` sur la session partagée — il ne peut donc PAS passer par cette session (piège 8). (e) Le cron `run()` n'écrit **rien** pour un compte en panne, pas même `last_stream_check` : avancer l'horodatage pousserait ces items hors de la fenêtre de re-check pour une panne dont ils ne sont pas responsables.

21. **Scraper manuel / verrou `match_locked` (§5.14) — les sept règles à ne pas défaire :**
    (a) **Ne JAMAIS simuler le verrou avec un drapeau existant** (`is_active`, `is_broken`, `is_in_allowed_categories`, un `content_rating` sentinelle…) : ces colonnes pilotent la génération `.strm`/NFO, `/dav`, les downloads et les lectures app (cf. piège 20). Le verrou vit dans **`media.match_locked`/`match_source`** (migration 026) et n'est lu que par les écrivains d'identité. Inversement, ne pas réutiliser `match_locked` pour masquer, filtrer ou désactiver quoi que ce soit.
    (b) **Tout nouvel écrivain de `imdb_id`/`tmdb_id`/`unification_id`/`history_group_key` doit honorer `match_locked`** — il n'y a **aucune** garde centrale, c'est une discipline par call-site. Les huit points existants : `enrichment_worker.py:585,632,689` (`_media_is_unlocked()` `:59`), `sync_worker.py:745-792`, `nfo_import_service.py:500-520`, `validate_id_consistency.py:442,525`, `dedup_resolved_twins.py:172`, `media_service.py:664-730,752`. ⚠️ Sur l'upsert de sync, la protection ne peut pas être une `COALESCE` : elle ne distingue pas « jamais rempli » de « **vidé exprès** », donc un id faux effacé par l'opérateur serait réinjecté au prochain `content_hash` changé. Le motif correct est `case((Media.match_locked == True, <colonne actuelle>), else_=<expression d'origine>)`.
    (c) **Le client image n'est JAMAIS celui de `tmdb_service`** (ni d'`omdb_service`) : `TMDBService._get_client()` injecte `api_key` en query-param sur **chaque** requête, donc télécharger un poster avec lui **fuite la clé API vers un hôte tiers** (potentiellement un panel Xtream). `poster_match_service` a son propre `httpx.AsyncClient`, **sans `params`**, vetté SSRF par `event_hooks` (`get_client`, `poster_match_service.py:346`), fermé au lifespan (`main.py:554`). Même règle pour les logs : jamais `str(exc)` d'une exception httpx TMDB/OMDb dans un message rendu ou loggé (l'URL, donc la clé, y est) — type d'exception + statut uniquement.
    (d) **Les types d'image scriptables sont rejetés, et le proxy envoie `nosniff`** : un `thumb_url` fournisseur répondant `image/svg+xml` serait servi **depuis l'origine `/admin`** (donc avec la Basic Auth ambiante de l'opérateur) et exécuterait du script. `_SCRIPTABLE_IMAGE_TYPES` (`poster_match_service.py:125,419`) refuse le SVG, `_ALLOWED_FORMATS` (`:122`) limite Pillow à JPEG/PNG/WEBP/GIF, et `GET /admin/media/{sid}/{rk}/poster` renvoie `X-Content-Type-Options: nosniff` (`admin.py:482`). Ne pas relâcher ces trois gardes. Le proxy ne prend **jamais** d'URL du client (l'URL est lue en base) — sinon c'est un proxy SSRF ouvert.
    (e-bis) **Le tiroir de scrape est une MODALE, et la fermeture passe par `window.plexhubScrape`** (`base.html`). Il rendait auparavant dans un bloc **au-dessus du tableau** : ouvrir le scraper depuis une ligne en bas de page mettait le formulaire hors écran, obligeant à remonter à chaque média (signalé à l'usage). C'est désormais un overlay `fixed inset-0` (`_scrape_panel.html`) portant `data-sid`/`data-rk`. Trois conséquences à ne pas défaire : (1) **ne jamais vider `#scrape-panel` directement** (`innerHTML = ''`) — passer par `plexhubScrape.close()`, qui retire aussi le `overflow-hidden` posé sur `<body>`, sinon la page reste **gelée après fermeture** ; (2) le contrôleur résout la ligne d'origine avec **`getElementById`, jamais `querySelector`** — même raison que le filtre `css_id` (un `rating_key` finit par `.mkv`, donc `#row-…-vod_439568.mkv` est un sélecteur invalide qui **lève**, cf. MS-04) ; (3) `close-scrape-panel` ne ferme plus seulement : il **enchaîne** sur la ligne suivante encore incomplète de la page (`data-incomplete="1"` posé par `_media_row.html`, où une ligne **verrouillée compte comme réglée**) et rouvre le tiroir avec **`?auto=1`**, seul cas où le formulaire de candidats se déclenche `on load`. Un clic manuel reste inerte : une auto-recherche y coûterait jusqu'à 3 appels TMDB + un repli OMDb + 5 téléchargements de posters à chaque simple coup d'œil. ⚠️ **Les captures d'écran CDP en mode plein-page ne rendent pas les éléments `position: fixed`** (image vide, alors que la modale est bien peinte) : vérifier une modale par `getBoundingClientRect` + `elementFromPoint`, pas par screenshot.
    (e) **htmx 1.x : deux pièges cumulés sur cet écran.** (1) htmx **ne swappe pas les réponses 4xx** — sans l'opt-in `htmx:beforeSwap` qui force `shouldSwap` sur **409 et 422 seulement** (`base.html:36`), un conflit d'identité rend le bouton « Appliquer » **muet** (le message que l'opérateur doit lire n'arrive jamais à l'écran). (2) Un `<div hx-swap-oob>` placé **à côté d'un `<tr>`** est **foster-parenté hors du tableau** par le parseur HTML et n'est donc jamais appliqué : la fermeture du tiroir passe par un événement `HX-Trigger: close-scrape-panel` + un auditeur `document` (`base.html:23`), **pas** par un OOB swap. (Rappel §5.10 : jamais de sélecteur `from:` contenant un espace, jamais de modificateur `changed` sur un `<form>`.)
    (f) **`count_requests()` est AGRÉGEANT en imbrication** (`tmdb_service.py:137-151`, `omdb_service.py:122-134`) : `RequestTally.add()` crédite la tally courante **et toutes les englobantes**. Une version non-agrégeante (celle que spécifiait l'ADR) **remet le budget du lot à zéro en silence** — `manual_scrape_service.search_candidates` ouvre son propre bloc, donc le worker ne voyait aucun appel de passe 2 et `budgetExhausted` ne pouvait jamais se déclencher sur le chemin le plus coûteux. Ne pas « simplifier » ce chaînage de parents.
    (g) **Un lot verrouille en masse, et il n'existe aucun déverrouillage groupé** (`unlock` est unitaire) : toujours un `dry_run=true` (zéro écriture, histogramme de distances) puis un lot à **`max_items` borné** avant d'envisager `SCRAPE_BATCH_POSTER_ONLY_AUTO=true`. Et les NFO/posters **déjà générés ne sont pas réécrits** après une correction d'identité (`LocalStorage`, AUDIT-P6-006) : l'opérateur doit vider les fichiers générés correspondants.

23. **Sauvegarde / restauration SQLite (Lot 10-A) — trois règles à ne pas défaire.** (a) **Ne JAMAIS laisser un `-wal`/`-shm` à côté d'un `plexhub.db` restauré** : SQLite rejoue le WAL périmé sur le fichier remplacé et corrompt la lecture — `restore_db` les supprime AVANT le `os.replace` (et après avoir conservé la base courante). (b) **Un backup n'est publié sous `plexhub-*.db` qu'après `integrity_check` ; ne pas écrire directement sous le nom final** (disque plein = fichier partiel qui ressemble à un backup valide, puis élagué comme les autres) ; le `.tmp` doit rester dans le MÊME dossier (même volume ⇒ `os.replace` atomique). Ne pas ajouter de `.db.tmp` au motif d'élagage : un `.tmp` récent peut être un backup en cours (le balayage > 1 h est séparé). (c) **`restore_db` ne doit pas exiger une base courante saine** : la copie préalable utilise `verify=False` avec repli en copie brute — une base corrompue est justement la raison d'une restauration. Le verrou `server_start.lock` s'ouvre en mode `"a"` (jamais `"w"` : ça tronquerait le pid écrit par le master). `fcntl` n'existe pas sous Windows : le script reste importable, le test réel de `flock` est `skipif`.

25. **Synchro EPG en masse / EPG (Lot 10-D, ADR 0006) — six règles à ne pas défaire.** (a) **Toute écriture d'`epg_entries` est un upsert sur `(server_id, stream_id, start_time)`** — jamais un `db.add` : l'unique `uix_epg_dedup` n'existait PAS en prod avant la migration 028 (la 006 ne le créait pas et `create_all` n'ajoute jamais d'index à une table existante), et un `ON CONFLICT` dont la cible ne correspond à aucun unique est **rejeté par SQLite**. Ne pas affaiblir la 028 en avalant son échec : sans l'index, chaque cache-miss et toute la synchro échouent à l'exécution. (b) **Ne jamais mettre l'XMLTV en mémoire** (`str`/`read()`), ne jamais le parser sur la boucle (`iter_programme_batches` s'avance par `asyncio.to_thread(next, gen, None)`) ; `get_xmltv` a été supprimée exprès — ne pas la ressusciter. Le plafond d'octets se mesure sur l'octet DÉCOMPRESSÉ. Un XMLTV déclarant des entités est refusé (scan du fichier ENTIER par blocs avec chevauchement) ainsi que tout UTF-16/UTF-32 ; le rempart complémentaire est la limite d'amplification d'expat. (c) **Jamais `str(exc)` d'une erreur httpx dans un log ou un rapport** : l'URL `xmltv.php?username=…&password=…` y est embarquée (`HTTPStatusError`) — type + code HTTP seulement (`_safe_error`) ; le logger `httpx` reste épinglé WARNING. (d) **Un lot = une transaction courte** (`EPG_SYNC_BATCH_SIZE`, 500) via `write_with_retry` : `EPG_SYNC_BATCH_SIZE` est borné à 2 000 (9 variables par ligne, limite SQLite 32 766) ; ne pas « optimiser » en une transaction par compte, elle tiendrait l'unique écrivain SQLite pendant des secondes (testé sous vrai verrou, `tests/test_epg_sync_real_lock.py`). (e) **La fenêtre est un CHEVAUCHEMENT**, pas « le début tombe dans la fenêtre » : un film commencé il y a 2 h et toujours à l'antenne est le « en cours » que le TV cherche. (f) **Livré DÉSACTIVÉ** (`EPG_SYNC_ENABLED=false` ⇒ le job n'est même pas enregistré) : la mesure à l'échelle de la base de prod (~1,9 Go) et de vrais XMLTV fournisseur n'a PAS été faite — `scripts/bench_epg_sync.py` n'est qu'un ordre de grandeur synthétique. Ne pas activer en production sans elle.

26. **Passerelle de scraping `/api/scrape/v1` (Lot B1, §5.15) — huit règles à ne pas défaire.**
    (a) **La passerelle n'écrit JAMAIS dans `tmdb_scrape_cache` ni `omdb_scrape_cache`** (caches du worker, garde-fou du lot) et ne lit pas le second : elle a sa propre table `scrape_cache` (module `scrape_gateway_cache`, à ne pas confondre avec `scrape_cache_service`), clé versionnée `"{key_version}|{language}|{key}"`. Toute évolution de `normalize_for_sorting` ⇒ `KEY_VERSION += 1` ; tout changement de forme d'un payload ⇒ `SCHEMA_VERSION += 1` (une entrée d'une autre version n'est jamais servie) ; le contrat machine se régénère (`REGEN_SCRAPE_OPENAPI=1`, `tests/test_scrape_v1_openapi_export.py`) et plexhubTMM est prévenu. Écritures par `write_with_retry` (session neuve par tentative), dans une transaction courte, **après** l'appel fournisseur — jamais de transaction ouverte pendant un appel TMDB/OMDb (piège 8).
    (b) **Une clé à scopes est confinée, et `verify_scrape_scope`/`verify_scrape_admin_scope` ne servent JAMAIS hors `/api/scrape/v1`** : ils laissent passer le maître ET la clé à scope mais REFUSENT une clé sans scope ; posés sur une route existante, ils ouvriraient cette route à la clé de plexhubTMM et la fermeraient aux clients historiques. `route_audit` ne les accepte que sous le préfixe PROPRE à chaque garde (`_SCOPE_GUARD_PREFIXES`, sinon boot refusé — vrai aussi pour `media.*` sous `/api/metadata/v1/`, piège 27) ; un nouveau préfixe ou garde de scope = une entrée de cette table + un test structurel route par route (`tests/metadata_api/test_routes_structure.py` pour B2), ne pas écrire de fabrique `verify_scope("x")` (une closure n'est pas reconnue par identité de fonction). Un nouveau scope = constante dans `api_key_service.KNOWN_SCOPES` + garde nommé + test structurel route par route. Ne pas rendre un scope « hiérarchique » : `scrape.admin` n'inclut pas `scrape`.
    (c) **Le vol partagé ne lève jamais, et aucune exception fournisseur ne sort en clair** : `_guarded` renvoie un `_FlightOutcome` dont l'erreur est une `GatewayError` NEUVE construite hors de tout bloc `except` (ni `__cause__` ni `__context__`) — `create_background_task` journalise toute exception de tâche avec `exc_info`, et une `HTTPStatusError` httpx embarque l'URL avec `api_key=`/`apikey=`. **Jamais `str(exc)`**, traceback, clé, URL fournisseur ou titre complet dans un journal ou un corps d'erreur : type + code HTTP seulement ; seule `ProviderError` s'échappe des méthodes strictes de `tmdb_service`/`omdb_service`. Chaque attendeur relève SA copie (`clone()`).
    (d) **Échéance et `shield`** : toute attente est sous `asyncio.timeout(SCRAPE_REQUEST_TIMEOUT_SECONDS)` (25 s, bornée 5..28) et le vol est attendu via `asyncio.shield` — la déconnexion d'un client ou l'échéance n'annule pas l'appel partagé, dont le résultat est quand même mis en cache. Ne pas retirer le `shield`. Un `Retry-After` TMDB plus long que le temps restant ⇒ 429 immédiat par `_request_bounded` (jamais 504). La consultation et l'insertion du vol (`_join_or_start`) ne contiennent aucun `await`.
    (e) **Langues en liste blanche** : `SCRAPE_ALLOWED_LANGUAGES` (défaut `fr-FR,en-US`, `TMDB_LANGUAGE` toujours acceptée), hors liste ⇒ 400. La langue fait partie de la clé : chaque langue distincte crée ses propres lignes, c'est la seule parade à la croissance de `scrape_cache` par multiplication des langues.
    (f) **Limite de corps 64 Kio et limiteur par clé** : `body_limit` est un middleware ASGI **pur** (pas `BaseHTTPMiddleware`, qui casserait le comptage des corps `chunked`) et n'agit que sous `/api/scrape/v1/` ; le limiteur (300/min par clé, `<= 0` désactive) compte toute requête authentifiée, 400 compris, via une dépendance déclarée **après** le garde (elle lit `request.state.principal`).
    (g) **État process-local** : single-flight (`_in_flight`), limiteur et compteurs `sinceStart` vivent en mémoire d'**un** process ⇒ ne jamais lancer `uvicorn --workers N>1` (pièges 7 et 18c) ; un redémarrage les remet à zéro. Les appels de la passerelle comptent dans les compteurs par passe du worker (aucun budget dédié, X3).
    (h) **La purge ne retire que les entrées expirées ou d'une version non courante** (`POST /cache/purge`, route seulement, **aucune purge automatique**, `limit` 1..100 000) : elle ne borne pas une croissance par variété de titres/années, l'opérateur la déclenche (`docs/33-ops-scrape-gateway.md` § 3). L'invalidation est tout ou rien (toutes les clés parsées avant toute suppression). Sur le homelab, un réglage `SCRAPE_*` doit être ajouté sous `environment:` du compose (le `.env` n'y est pas injecté).

27. **API d'édition des métadonnées `/api/metadata/v1` (Lot B2, §5.16) — sept règles à ne pas défaire.**
    (a) **Simulation et écriture partagent `plan_patch`** (`metadata_plan.py`, pur) ; la simulation n'ouvre aucune transaction d'écriture. Ne jamais ajouter de paramètre `dryRun` à une route d'écriture : un garde qui lit un paramètre de requête peut diverger de la lecture qu'en fait la route (élévation de privilège) — d'où des routes `…/preview` distinctes, sous `media.read`. `media.write` n'inclut pas `media.read`.
    (b) **Tout écrivain de `media` saute les lignes `match_locked` pour les colonnes de `metadata_columns.METADATA_WRITABLE_COLUMNS`.** `tests/test_media_writers_inventory.py` fige les 38 sites d'écriture (analyse AST) : un nouvel écrivain fait échouer le test — le garder ET le lister avec sa justification. Exceptions assumées (ADR 0012) : marquage adulte (`content_rating = XXX`), suppression de synchro d'un titre retiré du fournisseur, recalcul de `display_rating`. L'import NFO ne refait plus un id effacé, même en fill-missing.
    (c) **L'écriture réelle s'exécute dans `immediate_write_session`** : `BEGIN IMMEDIATE` AVANT toute lecture (sinon deux écrivains passent `If-Match` sur la même révision) ; `PRAGMA busy_timeout` abaissé à l'échéance le temps du `BEGIN` puis **restauré aussitôt** (une connexion du pool ne garde jamais la valeur courte) ; réponse préparée avant le `COMMIT` (aucune 5xx ensuite) ; **jamais de retry sur la même session** (piège 8) — le client rejoue avec la même `Idempotency-Key`. Testé sous vrai verrou WAL (`tests/metadata_api/test_real_lock.py`, `tests/test_immediate_write_real_lock.py`).
    (d) **La révision est une empreinte calculée** (aucune colonne, aucun autre écrivain modifié) : n'y mettre ni `updated_at`, ni `context`, ni colonnes d'images ; changer le jeu de champs hashé = incrémenter `REVISION_FORM`.
    (e) **Épisodes : `unification_id` et `history_group_key` ne sont jamais recalculés** (deux « Pilot » de séries différentes fusionneraient leurs historiques) ; l'annulation **restitue** les dérivés enregistrés (dont `display_rating`), elle ne les recalcule pas.
    (f) **Noms de modèles Pydantic uniques dans toute l'application** : deux modèles de même nom font préfixer les DEUX composants OpenAPI par leur module et cassent `scrape-v1.openapi.json` (d'où `MetadataErrorResponse`/`MetadataErrorDetail`). Contrat machine : `REGEN_METADATA_OPENAPI=1 pytest tests/metadata_api/test_openapi_export.py`, puis prévenir plexhubTMM.
    (g) **`BACKGROUND_JOBS_ENABLED=false` est réservé aux instances de test** : plus d'élection (donc plus d'`import fcntl`), de planificateur, de pipeline initial ni de workers ; `isMaster: false`. Jamais en production. Journal `metadata_edits` append-only (seul `reverted_by` est posé), sans purge automatique.
